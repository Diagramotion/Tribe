# Agent durability and reliability

## Goal

Let Tribe's standing project team complete long-horizon work across many model and tool steps, while preserving the user's intent, avoiding duplicate side effects, and reporting a clear recoverable state when work cannot continue.

## Design constraints

- Tribe's SQLite event log remains the authority for mission events, ownership, approvals, evidence, and completion. Pydantic AI Harness supplies model/tool capabilities and conversation checkpoints; it does not replace Tribe's mission lifecycle.
- A model context window is a per-request ceiling. Run token and cost budgets are cumulative controls across all requests in a run. Compaction keeps each request within the known model context; it must not consume or lower the independent run budget.
- Retry only transient failures at the layer that can identify them. Avoid multiplying SDK, transport, agent, and worker retries without a shared attempt and time budget.
- Resume from a durable model/tool frontier only when replay cannot duplicate an external side effect. Unknown tool outcomes remain quarantined for inspection.
- User cancellation, exact approvals, task claims, and repository policy remain authoritative across retry and recovery.
- Keep the local-first runtime usable without requiring Temporal, DBOS, or a hosted service. Evaluate a local SQLite durable-execution backend before adopting another execution service.

- Per-run `StepPersistence` snapshots and continuation use Pydantic AI Harness with a separate SQLite database.
- Startup recovery resumes a complete Harness snapshot only when both Harness and Tribe show no unresolved tool effects. When no checkpoint exists, it restarts from the original trigger only if no tool call ever started, rewinds that agent's event offset, and accounts for another attempt. Runs with any tool activity or unreadable checkpoint state remain quarantined.
- Provider retries use three short in-run attempts, then a durable retry schedule with jitter, bounded exponential backoff, provider `Retry-After`, a 24-attempt ceiling, and a persisted 24-hour retry window. Safe Pydantic AI retries continue the same trigger's saved checkpoint; retries stop after unexpected Tribe activity or an unresolved Harness tool-effect record. Completed repository tests, hash-reconciled repository writes, and explicitly configured read-only MCP calls are classified as safe durable results; unknown MCP writes remain fail-closed. Hidden provider retries are disabled for the default AI dependency set: OpenAI-compatible and Anthropic clients use zero SDK retries; Google direct and Gateway clients use one total attempt; Cohere's wrapper is set to zero retries; Mistral's retry strategy is set to `none`.
- Failed, retrying and interrupted run events now include a durable `failureKind`: transient provider, invalid request, usage limit, tool failure, policy denial, unknown side effect, or unknown. Side-effect uncertainty takes precedence over the original exception; interruptions mark an unknown side effect only when a tool start has no matching completion. Chat activity gives known failures and interrupted actions distinct explanations and keeps the raw diagnostic expandable. This is a run-level taxonomy; detailed tool failures still belong to their individual tool events.
- No cumulative token, request-count, or tool-call ceiling is applied by default to an agent run. Explicit project monthly-token, per-run-token, and per-run-cost budgets remain available for user-controlled limits. Model context stays bounded per request through compaction.
- In the live focus-timer mission, Planner's failed turn had nine model requests and eight repeated `finalize_plan` calls. The saved context estimate at failure was about 124,500 tokens against a 187,500-token compaction trigger (75% of the configured 250,000-token window), so compaction had not yet been triggered. The reported 1,062,017 input tokens were cumulative across requests; the same working history is normally sent again for each model request. This exposed that the default run budget could stop a multi-step turn before context compaction was needed, while repeated invalid tool calls made that turn particularly wasteful.
- A saved focus-timer trace contained 25 failed runs, 434 tool starts, 213 agent posts and 21 generated operational artifacts; the user had to correct evidence IDs and steer recovery several times before completion. This run does not satisfy autonomous delivery acceptance.
- Each completed provider response is now recorded immediately in an idempotent request-usage ledger, including model, token/cost usage, input-message count and compaction receipts present in the submitted history. Run totals update in the same transaction, so cancellation and process recovery retain usage already reported by the provider. A replayed response with the same timestamp key is not counted twice. The Runs view exposes these per-request metrics without conversation contents.
- Durable execution identities are defined by the existing storage keys: one logical agent run is `(agent_id, mission_id, trigger_sequence)`; attempts use the persisted run attempt number plus a unique per-run usage-reservation attempt; each provider response uses `(agent_id, mission_id, trigger_sequence, response_id)`, falling back to the Pydantic AI response timestamp and then a UUID only when the provider supplies neither; each tool effect uses Pydantic AI's `tool_call_id`, retained across Harness and Tribe tool/approval events. SQLite primary/unique constraints make run claims, request accounting and reservations idempotent. Tool-call identity alone does not make an external write safe to replay; unresolved effects remain quarantined unless explicitly reconciled.
- Startup recovery preserves a pending approval frontier and advances the consumer past its original trigger so it can receive the later decision. A resolved decision rewinds only that agent's cursor to the original trigger and resumes the saved deferred tool result; an approval already consumed before a crash is quarantined as an unknown outcome and never replayed. Store tests cover approved continuation and consumed-before-result crash recovery, and a worker-level restart test verifies the consumer replays the original trigger and settles the run. Broader end-to-end crash injection and live provider acceptance remain open.
- Long histories currently use Pydantic AI Harness compaction. Run usage, context-window metadata, monthly budgets, and cost budgets are enforced by Tribe.
- Compaction retains recent user turns alongside its incremental summary, reducing the chance that the user's original request disappears from a long run.
- Repository test commands return non-zero exit codes and captured output as tool results. Test-run records carry their originating tool-call ID; after a completed run, both the command records and matching tool-start/completion events are recognised as settled, so a subsequent transient provider failure can continue from the saved model/tool checkpoint and let the agent decide what to do next. An incomplete command remains unsafe to replay. Missing repository file reads return a `FILE_NOT_FOUND` result with a search recovery path, and agent instructions tell roles to use tool failures as feedback and adapt.
- Repository writes from both the Tribe write tool and Pydantic AI Harness filesystem now carry the originating tool-call ID through durable start/change events. If a process stops after the filesystem write but before Tribe records completion, recovery hashes the current file against its recorded expected hash and synthesises the matching change/completion events only on an exact match. Harness diffs that are incomplete or truncated do not yield an expected hash and remain quarantined. Harness must still report a safe checkpoint with no unresolved effect before the run resumes. Generated per-write diff artifacts were removed because Git Changes already owns the diff.
- MCP tool-start records carry the exact configured read-only classification. A completed read-only MCP call no longer makes a transient provider retry unsafe; write-capable MCP calls remain non-retryable after any activity unless their durable effect can be explicitly reconciled.
- `run_repository_tests` now returns both its run ID and the exact `verificationEventId` required by review checkpoints. Expected review/completion validation failures return structured `{ok: false, error, action}` tool results. Agents have separate profile-granted `message_agent` and `reply_to_agent` tools and may send multiple messages in a run; reply chains retain a loop guard. These paths are covered by tests, but live provider behaviour remains unverified.
- Repository diffs and command/test output are not user-facing artifacts. Repository test results stay in their verification events; Harness command output is retained on its durable tool-completion event, while Git Changes and Runs own operational history. The Artifacts view is reserved for deliverables. The chat task filters now remain in one horizontal row instead of wrapping across the message pane.
- Tool access is configured by each agent profile's `tool_permissions` list and filtered from its callable tool schema. The profile controls Tribe tools, Harness filesystem/shell capabilities, web access and MCP tools; missing grants mean no access. Role names do not grant capabilities. Repository read-only policy, approval gates and mission ownership remain independent runtime safety ceilings.
- Core planning, work-claim and review tools are eagerly loaded only when the profile grants them. Workflow discovery and selection are available to profiles with those grants; an Auto chat does not force a workflow, and an explicitly selected workflow cannot be silently replaced. A live goal-mission retry previously reported `Found 0 tools` when searching for `list_plan_items`; verify the provider request/tool adapter, not just the Python Agent schema, before considering this fixed.
- Tool-search guidance distinguishes deferred capabilities from eager core tools. A fresh live v7 mission exposed premature delivery-role wakeups during draft planning. Plan events are now routed by profile-granted capabilities, while planning and finalisation remain optional guidance; explicit task dependencies are the only plan edges that hold a claim.
- Plan-event wakeups require profile-granted plan/work capabilities. Messaging-only profiles no longer spend model calls reacting to plan creation, finalization or work completion events they cannot act on; the check is capability-based, not role-name-based.

It binds the checkpoint to the latest passing test inside the durable store transaction, while preserving strict latest-test-after-change validation and recording the resolved UUID in the checkpoint event. When an agent supplies evidence references, Tribe validates that they resolve to successful runs or mission artifacts. Stored IDs remain available for audit, but agent channel prose and rendered history hide them.

Replies should address a specific incoming message/thread. Bound runaway work through configurable per-run usage, duplicate/cycle detection, and explicit continuation semantics; replace the fixed hop count only after loop behaviour is measured.
- Keep artifacts semantically narrow. Final deliverables belong in Artifacts; command output and test reports belong in Runs/verification history; repository diffs belong in Git Changes. A patch or deletion diff may still be a review payload for an approval flow, but should not be presented as a finished deliverable. Audit remaining artifact producers and UI labels against this distinction.

## First implementation

The initial code change separates cumulative run budgets from per-request model settings, removes implicit cumulative token/request/tool-call ceilings, preserves explicit user-configured budgets, and switches from dropping old messages to incremental summaries. Follow-up changes add SQLite-backed retry deadlines for transient provider failures when the failed attempt emitted no mission activity; a replacement worker resumes these retries, users can cancel them, and an overall 24-hour window bounds wall-clock retries. On startup, Tribe resumes an abandoned run from a complete Harness snapshot only when both durable tool ledgers show no unsettled effects. When no checkpoint exists, it may replay the original trigger only if the run never started a tool call; it rewinds that agent's cursor and accounts for the new attempt. Any observed tool activity, pending approval or unreadable ledger remains quarantined. Idempotent reconciliation for other side effects and intervention-free long-horizon fault-injection acceptance remain open.
