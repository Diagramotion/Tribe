# Tribe Browser

## Product contract

Tribe Browser is a real browser surface embedded in the desktop shell. It renders the live page in its own browser engine and accepts native pointer, keyboard, touchpad and viewport input. A screenshot that is periodically refreshed from a separate headless session is not an implementation of this contract.

The user and an authorised agent operate on the same tab and browser context. Agent inspection and control must never silently attach to a second page with different cookies, storage, viewport or permissions. The embedded page remains isolated from Tribe's privileged application origin.

The Browser workspace includes familiar navigation and tab chrome, a visible editable address, back/forward/reload, progress and error state, viewport controls, and a clear way to manage the active profile and downloads. It must work with ordinary sites that prohibit iframe embedding. The web-only development preview cannot promise this: browser frame policies such as `frame-ancestors` and `X-Frame-Options` are enforced by the host browser.

## Engine architecture

The Browser implementation uses Electron's app-owned Chromium `WebContentsView` for the page and a sandboxed Electron renderer for Tribe's UI. The page has context isolation, no Node integration, web security and an isolated session partition. The privileged UI receives a narrow IPC bridge; page content does not receive Electron, CDP or Tribe credentials.

One Electron browser service owns profiles, tabs, navigation, viewport settings, permissions, downloads, storage and diagnostics. The visible Browser pane and authorised agent tools call that service, so both operate on the selected visible tab and its session. Agent calls go through an authenticated loopback service and are checked against the active project's host policy and action approvals.

Electron is the standard desktop release shell because the managed Browser depends on Chromium `WebContentsView`. Keep Tauri only as a legacy development path; do not publish it as the standard release while it cannot provide the managed Browser. Release CI must package and exercise Electron on every supported platform before publishing; do not fall back to an iframe or screenshot relay for arbitrary-site browsing.

The browser service owns an engine-neutral contract for browser profiles, contexts, tabs, navigation, viewport/emulation, page observation, input, permissions, storage inspection/clearing, downloads and lifecycle. Engine adapters implement that contract. Browser controls and agent tools call the same operations and reference the same tab identity.

## Profiles, data and downloads

- Support isolated temporary contexts and named persistent profiles. A chat starts isolated by default; sharing a persistent profile across chats must be an explicit user choice.
- Keep browser data in Tribe-managed profile directories, separate from the user's personal browser. Provide per-profile storage usage and controls to clear cache, cookies and site data. Do not expose raw cookie values or secrets to agents by default.
- Make downloads visible and durable: show progress, completion, failure and destination; let the user open or reveal a completed file. Downloads go to a managed directory first. Moving a download into a project repository is an explicit action.
- Support file upload through a scoped picker and exact action approval. Keep upload paths and entered values out of durable agent records.
- Show and manage site permissions, including camera, microphone, location, notifications, clipboard and pop-ups, with deny-by-default behaviour unless the user grants them.
- Provide a clear profile lifecycle: create, select, rename, clear data and delete, with confirmation for destructive data removal. Runtime shutdown must not corrupt persistent profiles.

## Agent browser capability

Agents need to build and verify web apps against the same page the user sees. The capability includes:

- Navigate, search and manage tabs; viewport presets and custom dimensions; device scale, touch and responsive emulation.
- Query the accessibility tree and DOM, find and inspect controls, click, fill, select, press keys and scroll. Keep coordinate actions for canvas and inaccessible controls.
- Capture screenshots on demand, inspect page errors and bounded console/network diagnostics, and verify rendered state after actions.
- Inspect and clear site data, manage permissions, upload files through policy and observe/await downloads.
- Report which profile, tab, URL origin, viewport and permission scope an action will affect.

Grant inspection and control separately. Apply project website access, exact one-time approvals where required, and clear boundaries around credentials, personal data, downloads and file access. Page content is untrusted input. Keep secrets, cookies, form values and page content out of durable history unless the user explicitly saves a reviewed result.

- Navigation, visible URL, history, tabs, pop-ups, reload/stop, downloads and a managed downloads dropdown.
- Isolated temporary and named persistent profiles, with cache/cookie/site-data status, clear controls and local profile lifecycle. Never read or expose raw cookies, passwords or secrets to agents by default.
- Explicit file upload and download policies. Keep downloads in a managed directory until the user chooses to reveal or move them into a repository.
- Site permission controls for camera, microphone, location, notifications, clipboard, pop-ups and other browser permissions. Deny by default until the user or policy allows them.
- Responsive viewport sizes, common device presets, custom dimensions, device scale, touch input, locale, reduced motion and network throttling where the engine supports them.
- Agent inspection of the accessibility tree and DOM, screenshots on demand, page/console/network diagnostics, semantic actions, text entry, native select-option inspection and selection, keyboard input, scrolling and coordinate actions for inaccessible controls.
- A user-visible active state and readable pointer/click indication when an agent is controlling the page. The user can stop agent control and can distinguish user from agent actions.
- Use a compact, flat blue pointer that matches the Workbench accent. Keep its hot spot aligned with the actual input point, use only a thin dark edge and subtle shadow, and fade it shortly after the action. Avoid glossy styling, oversized shapes and persistent overlays.

Page content is untrusted input. Keep it isolated from Tribe's privileged application origin. Apply project website access, exact approvals for sensitive actions, least-privilege file access and explicit user control over persistent profile reuse. Keep credentials, entered values, cookies, and page content out of durable history unless the user explicitly saves a reviewed result.

## Engine decision

Electron with `WebContentsView` is the selected prototype route. Its Chromium page, isolated session partitions, permission and download events, and authenticated same-tab agent bridge have been exercised in macOS development and unpacked-app checks. This is evidence for the browser architecture, not a release decision for the whole desktop shell.

The Electron shell must pass signed macOS packaging, Windows installer and lifecycle verification before a tagged release is published. Keep the browser page and agent automation on one Electron service; do not run different browser engines per platform or use an iframe/screenshot relay as a fallback.

Remaining release gates:

1. Verify a site with an explicit `frame-ancestors` or `X-Frame-Options` denial inside the packaged Browser surface.
2. Complete signed packaging, updates, permissions, recovery and native-view layout checks on every supported desktop platform; macOS functional packages used so far were unsigned.
3. Validate provider-driven browser tool selection with a model that emits structured function calls, not only the structured test models.
4. Close the documented legacy site-origin inventory and mobile-emulation gaps before calling the Browser complete.

If Electron cannot pass those gates without weakening security or breaking Tribe's native integrations, reassess another engine only with platform sandbox evidence. Do not run untrusted pages unsandboxed or expand the screenshot-forwarded preview into the Browser product surface.

## Shared browser service

One browser service owns profile, context, tab and download lifecycles. The workspace controls and agent tools call the same service. Define an engine-neutral contract for navigation, tabs, viewport/emulation, DOM/accessibility observation, input, storage clearing, permissions, file transfer and diagnostics. The engine adapter may use CDP internally, but untrusted page code must not receive CDP or Tauri privileges.

Browser profiles are explicit user data. The workspace browser uses an isolated temporary profile by default; users may deliberately select a named persistent profile when sign-in continuity is required. Its tabs and active profile belong to the browser workspace and remain separate from chat lifecycle. An authorised agent in an active chat may control the same visible tab under that project's exact-host policy. Store profiles beneath Tribe-managed app data, not the personal browser directory. Surface data size and destructive clear/delete controls. Downloads must be tracked with progress, destination, completion and failure state.
